# v0.3.0 — publication contrôlée

Ce document prépare une **future** version GitHub, il ne prouve pas que la release existe. La version publique courante reste v0.2.0 jusqu'à publication effective.

## Canal de diffusion retenu

- **Principal :** GitHub Releases, ZIP Windows x64 **sans installation de Node**, archive + somme SHA-256.
- **Secondaire :** sources GitHub clonables sur Windows/macOS/Linux avec Node.js 22+.
- **Optionnel, actuellement bloqué :** npm scoped package, tant que le propriétaire de `@neosoda` n'a pas effectué le bootstrap autorisé.

La v0.3.0 stabilise et documente les corrections post-v0.2.0 sans prétendre que le produit sait gérer à distance des machines ou effectuer toute modification MCP sensible depuis le navigateur.

## Conditions bloquantes pour publier sur GitHub

- [ ] `package.json` et racine `package-lock.json` contiennent **0.3.0**.
- [ ] `node dist/cli/index.js --version` retourne **0.3.0** ; le test automatisé lit le manifeste réellement installé.
- [ ] La PR de préparation est fusionnée dans `main`.
- [ ] Sur **le SHA exact de main**, les six jobs CI (Win/macOS/Ubuntu × Node 22/24), Chromium et packaging Windows sont terminés **success**.
- [ ] Le job Windows a vérifié le ZIP final extrait dans un chemin avec espaces, le Node embarqué, les versions, le serveur local sur un profil synthétique et le SHA-256.
- [ ] Le contenu du tarball npm, l'audit dépendances et la compilation sont réussis dans la CI.
- [ ] Vérifier l'absence d'un tag/release `v0.3.0` existant. **Ne jamais déplacer un tag publié**.
- [ ] Publier une release **v0.3.0** exactement sur le commit `main` validé, avec le contenu de `v0.3.0-release-notes.md` ; ne pas cocher une option qui sélectionnerait un autre commit.

## Publication automatisée sécurisée (PR de livraison)

Le workflow one-shot [`release-v0.3.0.yml`](../../.github/workflows/release-v0.3.0.yml) se déclenche sur les fins de **CI**, **Skill Hub browser QA** et **Windows portable package** pour les commits `main`.

Il vérifie le SHA **actuellement sur main**, la version 0.3.0 du paquet et du lockfile, les six jobs CI, les trois workflows en état `success` sur le **même SHA** et la présence de l'artefact Windows de cette exécution. Ensuite il télécharge ce ZIP testé, vérifie `.sha256`, et **crée directement la release v0.3.0 avec les deux assets**.

Une release créée avec `GITHUB_TOKEN` ne déclenche pas les workflows `release.published` habituels : ce workflow joint donc **directement** les deux fichiers, sans dépendre de `release-assets.yml`. Les releases créées manuellement gardent ce dernier workflow pour attacher leurs assets.

Le workflow refuse de déplacer un tag existant, ne réécrit pas les assets d'une release préexistante et quitte si `main` a changé entre-temps. **Il ne publie jamais une version qui a raté un contrôle.**

### Vérification après le workflow

1. Vérifier la fin du [workflow v0.3.0](https://github.com/neosoda/agent-commons/actions/workflows/release-v0.3.0.yml) et son étape « Create the public release with both Windows assets » (un job vert qui aurait simplement attendu les autres contrôles ne prouve pas une publication).
2. Ouvrir [la release v0.3.0](https://github.com/neosoda/agent-commons/releases/tag/v0.3.0) et confirmer que le tag correspond au SHA `main` validé.
3. Télécharger `AgentCommons-win-x64-portable.zip` et `.sha256`, vérifier qu'ils existent et que leur somme correspond.
4. Essai manuel conseillé sur un **PC Windows indépendant** : extraction hors dépôt, lancement `--home` isolé, test clavier/FR/EN et arrêt propre.

Si le workflow échoue faute de permission GitHub (`contents: write`), d'accès Actions ou pour une autre cause, **ne pas annoncer la release**. Corriger l'erreur ou recourir à [GitHub → Releases → Draft a new release](https://github.com/neosoda/agent-commons/releases/new) depuis le commit validé, puis laisser `release-assets.yml` joindre et valider le ZIP. Ne pas faire les deux à la fois ; éviter les tags concurrents.

**Vérification du ZIP sous PowerShell :**

```powershell
$zip = "AgentCommons-win-x64-portable.zip"
$expected = (Get-Content "$zip.sha256" -Raw).Trim().Split(' ')[0].ToLowerInvariant()
$actual = (Get-FileHash $zip -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $expected) { throw "Checksum invalide : ne pas executer l'archive." }
Write-Host "Archive verifiee : $actual"
```

## npm — action séparée du propriétaire

`publish.yml` nécessite désormais la variable repository **`NPM_PUBLISH_ENABLED=true`**. Tant qu'elle n'est pas activée, un événement `release.published` ne déclenche **aucune publication npm** : cela évite les anciens échecs E404 dus à l'absence de droits du scope. Le workflow reste disponible pour une exécution contrôlée.

**Avant d'activer cette variable :** le propriétaire doit se connecter au bon compte npm, vérifier ou créer le package `@neosoda/agent-commons` avec les permissions et 2FA nécessaires, configurer le Trusted Publisher GitHub (`neosoda/agent-commons`, workflow `publish.yml`, environnement `npm`) puis tester une publication sur une **version qui n'existe pas déjà**. Ne jamais inventer de token, ni affirmer npm publié sur la seule base d'un workflow déclenché.

## Ce qui reste hors automatisation

Essai de bout en bout depuis un téléchargement GitHub sur un poste Windows physique indépendant, NVDA/VoiceOver, signature du programme Windows et tests de comportement sous coupure brutale de courant/stockage. Ces contrôles sont recommandés avant de qualifier le produit de distribution grand public complètement auditée, mais ne bloquent pas une mise à disposition transparente du ZIP GitHub.
